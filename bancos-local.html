Banco de dados local: sqlite3 e PostgreSQL no celular

Seu app no celular precisa guardar dados? Você tem duas ótimas opções sem sair do Termux: o SQLite (um banco inteiro num único arquivo .db — perfeito para apps mobile) e o PostgreSQL 16.2 completo, rodando no próprio celular para testes e projetos maiores. Nesta aula você instala, cria um banco, cria tabela, insere e consulta — tudo na máquina ana@android.

Você vai aprender
  • Instalar: pkg install sqlite e pkg install postgresql.
  • SQLite: sqlite3 meu.db "select 1;" → imprime 1; .tables → usuarios produtos.
  • Criar tabela e inserir dados num arquivo .db na home.
  • PostgreSQL no Termux: inicializar o cluster, subir o serviço e entrar com psql.
  • Quando usar cada um (tabela comparativa).
  • Como o banco conversa com o servidor web da aula anterior (python + sqlite no mesmo celular).

SQLite: um banco inteiro num arquivo

O SQLite não tem servidor — o banco é um arquivo só (meu.db), e a biblioteca abre ele direto. Ideal para apps no celular: os dados ficam na home do Termux e dá para copiar o arquivo como backup.

$ pkg install sqlite
...
sqlite instalado ✓
$ sqlite3 --version
3.45.1 2024-01-15

O primeiro teste: select 1

O comando de "está vivo?" do SQL:

$ sqlite3 meu.db "select 1;"
1

Se imprimiu 1, o banco abriu e respondeu. Note a sintaxe: sqlite3 ARQUIVO "COMANDO SQL" — o banco é o primeiro argumento, o SQL vai entre aspas (porque tem ponto e vírgula, que o shell engoliria se não fosse pelas aspas).

Vendo as tabelas: .tables

Comandos que começam com . são comandos internos do sqlite3, não SQL:

Missão: rode sqlite3 meu.db ".tables" (com as aspas!). A saída deve ser usuarios produtos — as duas tabelas do banco da Ana.

$ sqlite3 meu.db ".tables"
usuarios  produtos
$ sqlite3 meu.db ".schema usuarios"
CREATE TABLE usuarios (
  id INTEGER PRIMARY KEY,
  nome TEXT NOT NULL,
  email TEXT
);
sqlite3
O cliente de linha de comando do SQLite.
meu.db
O arquivo do banco — se não existir, o sqlite3 cria na hora.
".tables"
Comando interno (ponto) que lista as tabelas. Aspas porque o shell trata . normal, mas manter as aspas é boa prática com comandos SQL.

Criando tabela, inserindo e consultando

Fluxo completo num banco novo — o que um app faria por baixo dos panos:

$ sqlite3 meu.db
sqlite> CREATE TABLE produtos (id INTEGER PRIMARY KEY, nome TEXT, preco REAL);
sqlite> INSERT INTO produtos (nome, preco) VALUES ('café', 4.50), ('pão de queijo', 3.00);
sqlite> SELECT * FROM produtos;
1|café|4.5
2|pão de queijo|3.0
sqlite> SELECT nome FROM produtos WHERE preco < 4;
pão de queijo
sqlite> .quit
$ ls -lh meu.db
-rw------- 1 u0_a231 u0_a231 12K meu.db

Dentro do prompt sqlite>, cada comando SQL termina com ;. O .quit (ou Ctrl+D) sai. Repare que o banco inteiro virou um arquivo de 12 KB na home — dá para dar scp dele para o PC (aula sshd) como backup.

#!/data/data/com.termux/files/usr/bin/python
import sqlite3

# o banco vive na mesma pasta do app
con = sqlite3.connect("meu.db")
cur = con.cursor()
for linha in cur.execute("SELECT nome, preco FROM produtos"):
    print(linha)
con.close()

Esse é o jeito real de usar: o Python (ou Node, ou qualquer linguagem) abre o .db com a biblioteca padrão sqlite3 — sem servidor, sem porta, sem senha. É por isso que SQLite é o banco padrão de apps mobile.

PostgreSQL no Termux: o "banco de gente grande" no bolso

Para projetos maiores ou para aprender SQL de verdade, o Termux traz o PostgreSQL completo — o mesmo que roda em servidores de produção:

Missão: rode psql no terminal. A saída deve mostrar PostgreSQL 16.2 no Termux ✓ — a versão do servidor de banco instalada no celular da Ana.

$ pkg install postgresql
...
postgresql instalado ✓
$ psql
PostgreSQL 16.2 no Termux ✓
psql -U postgres -d meubanco (simulado)

Num Termux real, depois de instalar você inicializa o cluster de dados e sobe o serviço:

$ initdb ~/pgdata            « cria o cluster em ~/pgdata
$ pg_ctl -D ~/pgdata -l ~/pg.log start   « liga o servidor postgres
$ psql -U postgres -d meubanco
meubanco=# CREATE TABLE teste (id int);
meubanco=# \q
PostgreSQL no celular é para desenvolvimento e estudo — não exponha a porta 5432 na rede. O Termux roda o postgres como usuário comum, sem systemd; para parar, use pg_ctl stop. Para produção de verdade, use um servidor dedicado (ou o proot-distro com systemd, no nível 2).

Regra prática: começou no celular → SQLite. Vai virar um serviço com vários acessos → PostgreSQL (e depois migra o mesmo SQL para um servidor de verdade, porque a linguagem é a mesma).

Banco + servidor web no mesmo celular

Juntando com a aula servidor web: o servidor Python serve páginas e o SQLite guarda os dados — tudo no mesmo aparelho, na mesma pasta:

$ cd ~/projetos/meu-site
$ ls
app.py  meu.db  index.html
$ python -m http.server 8080
Serving HTTP on 0.0.0.0 port 8080 (http://192.168.1.42:8080/ ) ...
« o app.py abre meu.db com sqlite3.connect e responde as páginas
« de outro aparelho na Wi-Fi: http://192.168.1.42:8080 funciona

Essa é a stack mínima de um projeto full-stack de bolso: HTTP (python) + banco (sqlite) + arquivos (~/storage), tudo no Termux.

Operações do dia a dia no SQLite

Além de criar e consultar, você vai precisar atualizar, apagar e fazer backup:

$ sqlite3 meu.db
sqlite> UPDATE produtos SET preco = 5.00 WHERE nome = 'café';
sqlite> DELETE FROM produtos WHERE nome = 'pão de queijo';
sqlite> SELECT count(*) FROM usuarios;
7
sqlite> .backup ~/backup-meu.db     « backup quentinho do banco inteiro
sqlite> .quit
$ sqlite3 meu.db ".dump" | head -5
PRAGMA foreign_keys=OFF;
BEGIN TRANSACTION;
CREATE TABLE usuarios (…);
INSERT INTO usuarios VALUES(1,'Ana','ana@exemplo.com');
  • .backup ARQUIVO — copia o banco com segurança (melhor que cp com banco aberto);
  • .dump — despeja o banco inteiro como SQL texto (ótimo para migrar de aparelho);
  • DROP TABLE produtos; — apaga a tabela inteira (cuidado: sem lixeira no SQL);
  • VACUUM; — compacta o arquivo depois de muitos DELETEs.
#!/data/data/com.termux/files/usr/bin/bash
# backup diário do banco para a pasta compartilhada
sqlite3 ~/projetos/meu-site/meu.db ".backup ~/storage/downloads/meu-db-$(date +%F).db"
echo "backup do banco concluido"

Esse script é o primo do ~/backup.sh da Ana (que compacta as fotos) — dá para agendar os dois no crontab (nível 2) e mandar o backup para o PC com rsync via SSH.

SQLite bloqueia escrita simultânea: se dois processos escreverem no mesmo .db ao mesmo tempo, um recebe database is locked. Em app de celular isso raramente acontece (um app só), mas em servidor web com várias requisições, use o modo WAL: PRAGMA journal_mode=WAL; — ou parta para o PostgreSQL.

No PostgreSQL a sintaxe é a mesma (é o mesmo SQL) — só muda o prompt: meubanco=# em vez de sqlite>, e os comandos internos começam com \ (barra invertida): \dt lista tabelas, \q sai, \l lista bancos.

Erros comuns de SQL no terminal

Error: near "…": syntax error — quase sempre esqueceu o ponto e vírgula no fim do comando SQL dentro do sqlite>. No sqlite3 interativo, o comando só roda quando você fecha com ; e aperta Enter.
Error: no such table: produtos — você abrió outro arquivo .db (o sqlite3 cria um vazio na hora se o nome não existe!). Confira com .tables e com ls -lh *.db qual banco está aberto.
database is locked — outro processo está escrevendo no mesmo banco. Espere alguns segundos e tente de novo; se persistir, ative o modo WAL (PRAGMA journal_mode=WAL;) ou migre para o PostgreSQL.

Resumo

  • SQLite: banco inteiro num arquivo .db; pkg install sqlite; sqlite3 meu.db "select 1;" imprime 1.
  • sqlite3 meu.db ".tables" lista as tabelas → usuarios produtos; .schema mostra o CREATE TABLE.
  • Fluxo: CREATE TABLE → INSERT → SELECT → .quit; backup = copiar o arquivo.
  • PostgreSQL 16.2 roda completo no Termux: pkg install postgresql, initdb, psql → PostgreSQL 16.2 no Termux ✓.
  • Use SQLite para dados locais de app; PostgreSQL para estudo/projetos que um dia sobem para servidor.
  • Stack de bolso: python http.server (HTTP) + sqlite (dados) + ~/storage (arquivos) no mesmo celular.
