termux-job-scheduler e crontab: o celular trabalha sozinho

Imagine o backup das suas fotos rodando sozinho a cada 30 minutos, sem você abrir o Termux. No Android não existe um "cron do sistema" como no Linux de PC, mas o Termux oferece duas ferramentas para isso: o crontab (a agenda clássica do Unix, que já está configurada na máquina da Ana) e o termux-job-scheduler (a API do Android para agendar scripts). Nesta aula você vê os dois funcionando em ana@android.

Você vai aprender
  • O que já está agendado na máquina da Ana: crontab -l mostra o backup a cada 30 minutos;
  • A sintaxe cron de 5 campos: minuto hora dia-do-mês mês dia-da-semana;
  • termux-job-scheduler --script ~/backup.sh --period 300000: agendar um script com período em milissegundos;
  • Ler o resultado do backup: cat backup.log e cat backup.sh;
  • O limite importante: jobs só rodam com uma sessão do Termux viva — e é aí que entra o wake lock.

O cenário da Ana: backup da galeria

A Ana guarda as fotos do celular na pasta DCIM compartilhada (lembra do termux-setup-storage?) e criou um script que empacota essa pasta num .tar.gz. Olhe o home dela e o conteúdo do script e do log:

$ ls
backup.sh  storage  .bashrc  .termux  projetos
$ cat backup.sh
#!/data/data/com.termux/files/usr/bin/bash
echo "backup iniciado"
tar -czf ~/backup.tar.gz ~/storage/shared/DCIM
echo "backup concluido"
$ cat backup.log
backup iniciado
backup concluido
backup iniciado
backup concluido

O backup.log já mostra duas execuções — ou seja, algo já está rodando esse script sozinho. É o crontab. Vamos ver a agenda:

$ crontab -l
# crontab do Termux (ana@android)
*/30 * * * * ~/backup.sh >> ~/backup.log 2>&1

Essa linha diz: "a cada 30 minutos, rode ~/backup.sh e jogue a saída (e os erros, por causa do 2>&1) no fim do ~/backup.log". É exatamente o que aparece no log: "backup iniciado / backup concluido" repetido.

A sintaxe do cron (5 campos)

Toda linha do crontab (fora os comentários com #) tem cinco campos de tempo seguidos do comando:

*/30 * * * * ~/backup.sh >> ~/backup.log 2>&1
│    │ │ │ └─ dia da semana (0-6, 0 = domingo)
│    │ │ └─── mês (1-12)
│    │ └───── dia do mês (1-31)
│    └─────── hora (0-23)
└──────────── minuto (0-59)
CampoValoresSignificado
1º — minuto0–59* = todo minuto; */30 = de 30 em 30 minutos
2º — hora0–233 = 3h da manhã
3º — dia do mês1–311 = todo dia 1º
4º — mês1–1212 = dezembro
5º — dia da semana0–6 (0 = domingo)1 = segunda-feira
ExpressãoQuando rodaUso típico no Termux
*/30 * * * *a cada 30 minutosbackup incremental da DCIM (o caso da Ana)
0 3 * * *todo dia às 3hbackup completo noturno
0 8 * * 1segunda-feira às 8hrelatório semanal

Erros clássicos de cron: (1) escrever 4 campos (*/30 * * *) — o comando roda no horário errado; (2) confundir a ordem (hora vem depois do minuto); (3) esquecer que o cron usa o horário do sistema do celular — se o Android estiver em outro fuso, "3h" não é 3h pra você. Para editar a agenda num celular real, use crontab -e (abre o editor padrão, ex.: vim) — no simulador, crontab -e só mostra uma mensagem de brincadeira.

termux-job-scheduler: agendar pelo Termux-API

Além do crontab, o Termux tem uma API própria para agendar scripts usando o JobScheduler do Android — o termux-job-scheduler. A sintaxe é diferente e o detalhe que mais confunde é a unidade do período:

$ termux-job-scheduler --script ~/backup.sh --period 300000
Job agendado (id 1): ~/backup.sh a cada 300000 ms ✓
--script ~/backup.sh
o caminho do script que será executado — precisa ser executável e com shebang (#!/.../bash).
--period 300000
o intervalo em milissegundos: 300000 ms = 5 minutos. Esse é o erro nº 1: não é segundos!
Job agendado (id 1)
o Android devolve um id para o job — dá para cancelar depois com --cancel id.
Período desejadoValor para --period (ms)Comando
5 minutos300000termux-job-scheduler --script ~/backup.sh --period 300000
30 minutos1800000... --period 1800000
1 hora3600000... --period 3600000
1 dia86400000... --period 86400000
Limite real e importante: tanto o crontab quanto o termux-job-scheduler só rodam enquanto existe uma sessão do Termux viva (ou com os serviços do Termux ativos). Se o Android matar o app, o job não roda. Para backups/servidores de madrugada isso muda tudo — é por isso que a próxima aulas depois desta trilha é o wake lock (termux-wake-lock), que segura a CPU e a tela ligadas, e o sshd (aula de SSH no celular) para manter uma sessão sempre aberta.

Juntando as peças: aviso + log + agendamento

Um script bem comportado para rodar sozinho precisa de duas coisas: gravar a própria saída num log (é o >> ~/backup.log 2>&1 do crontab) e deixar uma pista visível de que rodou — o toast da aula anterior cai muito bem aqui:

#!/data/data/com.termux/files/usr/bin/bash
echo "backup iniciado"
tar -czf ~/backup.tar.gz ~/storage/shared/DCIM
termux-toast "backup concluido ✓"
echo "backup concluido"

Com a linha do termux-toast, cada execução do job deixa um pop-up na tela do celular — útil quando o backup roda enquanto você usa o celular. E no log, cat backup.log continua acumulando "backup iniciado / backup concluido", como vimos acima.

Missões no simulador

Na máquina ana@android, cheque a agenda existente e crie um job novo:

Missão: agende o backup da Ana a cada 5 minutos com termux-job-scheduler --script ~/backup.sh --period 300000 — a saída confirma Job agendado (id 1): ~/backup.sh a cada 300000 ms ✓.

Missão: veja a agenda existente com crontab -l — a linha */30 * * * * ~/backup.sh >> ~/backup.log 2>&1 mostra o backup a cada 30 minutos. Depois rode cat backup.log para ver as execuções.

Editando a agenda: crontab -e e o arquivo do crontab

Para mudar a agenda num celular real, o comando é crontab -e: ele abre o crontab no editor padrão (vim ou nano, conforme a aula de editores). Cada linha segue a regra dos 5 campos + comando. Um arquivo de crontab típico da Ana, com o backup de 30 em 30 minutos e uma limpeza semanal:

# crontab do Termux (ana@android)
# backup da galeria a cada 30 minutos
*/30 * * * * ~/backup.sh >> ~/backup.log 2>&1
# todo domingo às 23h, limpa logs com mais de 7 dias
0 23 * * 0 find ~/projetos -name "*.log" -mtime +7 -delete
# às 3h todo dia, foto da câmera frontal + backup completo
0 3 * * * termux-camera-photo --camera 1 ~/storage/shared/DCIM/auto-$(date +\%H\%M).jpg

O detalhe chato de cron dentro de scripts: o % precisa ser escapado (\%) porque no crontab o % vira quebra de linha. No exemplo acima, a forma correta dentro do crontab é date +\%H\%M.

Erros reais de agendamento no Termux: (1) script sem permissão de execução — rode chmod +x ~/backup.sh antes de agendar; (2) --period em milissegundos, não segundos (300000 = 5 min); (3) caminho relativo no cron dá errado — use caminho absoluto (~/backup.sh vale porque o cron do Termux roda na home); (4) o job não rodou de madrugada porque o Termux estava morto — resolva com wake lock ou mantendo uma sessão SSH aberta.

crontab ou termux-job-scheduler: qual usar?

As duas ferramentas se sobrepõem, mas têm jeitos diferentes. Na prática, muita gente usa as duas:

crontabtermux-job-scheduler
Sintaxe5 campos cron + comando (ex.: */30 * * * *)parâmetros: --script, --period (ms)
Onde vivearquivo do crontab (crontab -l / -e)agenda do JobScheduler do Android (tem id: Job agendado (id 1))
Granularidade1 minuto no mínimomilissegundos (dá para 5 min, 30 s...)
Persistênciaenquanto o serviço de cron do Termux estiver vivoo Android pode segurar o job mesmo entre reinícios do app (melhor para "uma vez por dia")
Ver o que rodouvocê mesmo manda pro log (>> ~/backup.log 2>&1)saída vai para o log do sistema (logcat) ou para o log que o script gravar

Regra prática: use o crontab para rotinas recorrentes com cara de servidor (backup a cada 30 min, limpeza semanal) e o termux-job-scheduler para tarefas pontuais ou com período "estranho" que o Android gerencia melhor. E para ambos: teste primeiro rodando o script na mão (~/backup.sh) e conferindo cat backup.log antes de confiar na agenda.

Convertendo períodos para milissegundos

Como o --period é em milissegundos, a conversão mental é: segundos × 1000.. Exemplos rodando na máquina da Ana:

$ termux-job-scheduler --script ~/backup.sh --period 300000
Job agendado (id 1): ~/backup.sh a cada 300000 ms ✓
$ termux-job-scheduler --script ~/backup.sh --period 1800000
Job agendado (id 2): ~/backup.sh a cada 1800000 ms ✓
$ termux-job-scheduler --script ~/backup.sh --period 86400000
Job agendado (id 3): ~/backup.sh a cada 86400000 ms ✓

Ou seja: 300000 = 5 min, 1800000 = 30 min, 86400000 = 24 h. Cada chamada devolve um id novo (1, 2, 3...) — guarde o id se quiser cancelar depois. Se você passar um período muito curto (ex.: 1000 ms = 1 segundo), o Android pode recusar ou rodar o job o tempo todo — o sistema tem um período mínimo efetivo.

Resumo

  • crontab -l lista a agenda; no simulador já existe */30 * * * * ~/backup.sh >> ~/backup.log 2>&1 (backup a cada 30 min).
  • Sintaxe cron: minuto hora dia-do-mês mês dia-da-semana + comando; */30 = de 30 em 30 minutos.
  • termux-job-scheduler --script ~/backup.sh --period 300000 agenda via API do Android e confirma Job agendado (id 1) ... ✓.
  • --period é em milissegundos: 300000 = 5 min, 1800000 = 30 min, 86400000 = 1 dia.
  • Saída para log com >> arquivo 2>&1; aviso na tela com termux-toast.
  • Jobs só rodam com o Termux vivo — para rodar de madrugada, estude wake lock.
